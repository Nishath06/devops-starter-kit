# ⚙️ GitHub Actions CI/CD Configuration Guide

This guide details the configuration settings, secrets, repository variables, and naming conventions required for the reusable CI pipelines in this GitOps starter platform.

---

## 🔒 Required GitHub Secrets

Configure these secrets in your GitHub application repository under:  
**Settings ➔ Secrets and variables ➔ Actions ➔ Secrets ➔ New repository secret**

| Secret Name | Required | Scope / Purpose | Recommended Generation Method |
| :--- | :---: | :--- | :--- |
| `DOCKERHUB_USERNAME` | **Yes** | Docker Hub username or organization account | Docker Hub account profile |
| `DOCKERHUB_TOKEN` | **Yes** | Docker Hub Personal Access Token (PAT) with Read & Write permissions | [hub.docker.com/settings/security](https://hub.docker.com/settings/security) |
| `GH_PAT` | **Yes** | GitHub Personal Access Token (classic or fine-grained) with `repo` scope to create PRs in your infrastructure repository | [github.com/settings/tokens](https://github.com/settings/tokens) |
| `SONAR_TOKEN` | No | SonarQube authentication token | SonarQube -> My Account -> Security -> Generate Token |
| `SONAR_HOST_URL` | No | SonarQube instance URL (e.g. `https://sonar.company.com`) | Your internal or SonarCloud instance URL |

> [!WARNING]
> Never hardcode credentials into workflow YAML files or commit `.env` files. Ensure `GH_PAT` has write access to the target GitOps infrastructure repository, or PR creation will fail with `HTTP 403 Forbidden`.

## 🏷️ Required Repository Variables

Configure these variables in your GitHub application repository under:  
**Settings ➔ Secrets and variables ➔ Actions ➔ Variables ➔ New repository variable**

| Variable Name | Required | Default Value | Description | Example |
| :--- | :---: | :---: | :--- | :--- |
| `INFRASTRUCTURE_REPO` | **Yes** | — | Target GitOps infrastructure repository (`owner/repo`) | `my-org/starter-app-infrastructure` |
| `PROJECT_NAME` | No | `starter` | Service / project name prefix for container images and SonarQube keys | `ecommerce-api` |

## 🏷️ Standard Naming Conventions

### 1. Docker Image Naming Convention

All built images follow this production naming standard:

```text
docker.io/<DOCKERHUB_USERNAME>/<PROJECT_NAME>-<COMPONENT>:<TAG>
```

#### Examples:
* **Backend Commit SHA Tag**:  
  `docker.io/octocat/starter-backend:a1b2c3d`
* **Backend Latest Tag**:  
  `docker.io/octocat/starter-backend:latest`
* **Frontend Commit SHA Tag**:  
  `docker.io/octocat/starter-frontend:a1b2c3d`
* **Frontend Latest Tag**:  
  `docker.io/octocat/starter-frontend:latest`

---

### 2. GitOps Branch Naming Convention

When a pipeline pushes an image and initiates an infrastructure update, it isolates the change inside a dedicated feature branch in the infrastructure repository:

```text
update/<COMPONENT>-image-<GIT_SHA>
```

#### Examples:
* `update/backend-image-a1b2c3d`
* `update/frontend-image-a1b2c3d`

---

### 3. Git Commit Message Convention

All automated commits to the infrastructure repository follow the **Conventional Commits** standard:

```text
chore(gitops): update <COMPONENT> image to <GIT_SHA>
```

#### Examples:
* `chore(gitops): update backend image to a1b2c3d`
* `chore(gitops): update frontend image to a1b2c3d`

---

### 4. Pull Request Naming & Body Convention

#### PR Title:
```text
Update <Component> Image to <GIT_SHA>
```

#### PR Body Structure:
```markdown
## 🚀 Automated GitOps Image Update

This Pull Request was automatically generated by the upstream CI pipeline.

### 📦 Deployment Details
| Parameter | Value |
| :--- | :--- |
| **Component** | `backend` |
| **Target Environment** | `dev` |
| **Docker Image** | `docker.io/octocat/starter-backend:a1b2c3d` |
| **Commit SHA** | `a1b2c3d` |
| **Target Values File** | `environments/dev/values.yaml` |
| **Source Workflow Run** | [View CI Run](https://github.com/my-org/my-app/actions/runs/12345678) |

### ⚙️ GitOps Reconcile Action
Once merged, **ArgoCD** will detect this commit and automatically synchronize the deployment to Kubernetes without downtime.
```

## 🚀 Environment Progression Flow

The pipelines support multi-environment GitOps updating via either:
1. Automatic branch triggers:
   * Pushes to `main` branch trigger PRs against `dev` environment.
2. Manual triggers (`workflow_dispatch`):
   * Select `dev`, `staging`, or `prod` from the GitHub Actions UI dropdown to open an update PR targeting `environments/<env>/values.yaml`.
